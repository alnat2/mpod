# Экспертный анализ: NotAllowedError на iPhone при переходе глав

## Вердикт

**Гипотеза предыдущего агента верна, и я могу точно показать механизм сбоя в коде.** Проблема — в `switchAudio()`: при переходе к заранее подготовленному аудио приложение заменяет активный `HTMLAudioElement` на совершенно новый. iOS Safari отклоняет `play()` на таком элементе, потому что он не был «благословлён» пользовательским жестом.

---

## Точный путь ошибки в коде

### Шаг 1: Подготовка нового Audio-элемента

В `prepared-audio.ts:10` создаётся **новый** `HTMLAudioElement`:

```ts
const audio = new Audio();  // ← совершенно новый элемент, без user gesture
```

Ему назначается `src`, вызывается `load()`, настраивается позиция. Элемент получает данные, но **никогда не получал разрешение на воспроизведение через user gesture**.

### Шаг 2: Завершение главы запускает переход

В `use-playback-audio.ts:942-1041` при `completeCurrentPlayback()`:
- Вычисляется `synchronousNextItem`
- Вызывается `startQueuedEpisode(synchronousNextItem)` (строка 1041)

### Шаг 3: startQueuedEpisode берёт подготовленный элемент

В `use-playback-audio.ts:454-477`:

```ts
const preparedAudio = prepared?.ownerGeneration === sourceGenerationRef.current &&
  prepared.revision === queueRevisionRef.current && 
  prepared.sourceKey === playbackMediaSourceKey(episode) &&
  prepared.controller.position === nextPosition 
    ? prepared.controller.take()   // ← забирает новый Audio-элемент
    : null;

// ...
if (preparedAudio) switchAudio(preparedAudio);  // ← КРИТИЧЕСКАЯ СТРОКА
```

### Шаг 4: switchAudio заменяет активный элемент

В `use-playback-audio.ts:1216-1226`:

```ts
const switchAudio = (nextAudio: HTMLAudioElement) => {
  const previous = audio;
  detachAudio();
  audio = nextAudio;           // ← теперь "audio" — новый элемент
  audioRef.current = nextAudio;
  bindAudio(nextAudio);
  previous.pause();
  // old element destroyed
};
```

После этого `audio` переменная и `audioRef.current` указывают на **новый элемент**, который никогда не имел user gesture.

### Шаг 5: tryPlay вызывает play() на новом элементе

В `use-playback-audio.ts:727-731`:

```ts
if (preparedAudio || nextPosition === 0) {
  setPositionSeconds(nextPosition);
  if (playingRef.current) {
    void tryPlay();  // ← вызовет audio.play() на новом элементе
  }
}
```

И в `tryPlay` (строка 631):

```ts
const playPromise = attemptAudioPlay(audio, () => {});
```

Здесь `audio` — это уже `switchAudio`-ный новый элемент. **iOS Safari выбрасывает `NotAllowedError`.**

### Шаг 6: NotAllowedError не обрабатывается как recoverable

В `use-playback-audio.ts:647-673`:

```ts
if (error) {
  const isNotSupported = error.name === "NotSupportedError";
  if (isNotSupported && playAttempts < MAX_PLAY_ATTEMPTS) {
    // retry логика — только для NotSupportedError
  }
  // NotAllowedError попадает сюда:
  playingRef.current = false;
  setPlaying(false);
  setPlaybackError(describeAudioError(error));  // ← показывает ошибку
  cancelAutoPlay();                              // ← остановка
}
```

**Retry предусмотрен только для `NotSupportedError`**, а `NotAllowedError` сразу останавливает воспроизведение.

## Почему «через главу»

> [!IMPORTANT]
> Паттерн «через главу» объясняется тем, когда подготовленный элемент успевает стать ready.

Подготовка (`prepareNextAudio`) запускается в `prepareNext()` (`use-playback-audio.ts:414-439`) — при `onPlaying`, `onTimeUpdate` и `visibilitychange`. Она проверяет множество условий (строки 415-438):

- `preparedRef.current` должен совпадать по `revision`, `ownerGeneration`
- Нужен кеш треков (`audiobookTracksCacheRef`)
- Элемент должен пройти `isReady()` — `readyState >= HAVE_FUTURE_DATA`, позиция применена, буфер достаточный

**Если подготовка успела завершиться** → `take()` возвращает новый элемент → `switchAudio` → `NotAllowedError`.

**Если подготовка НЕ успела** (кеш ещё не загрузился, сеть медленная, слишком короткая глава) → `take()` возвращает `null` → `cancelPrepared()` → используется **тот же `audio` элемент** через `primeAudioSource` → **работает**, потому что элемент унаследовал user gesture.

Короткие главы не дают времени на подготовку → fallback → успех. Длинные главы дают время → подготовка завершена → `switchAudio` → ошибка. Чередование коротких/длинных глав создаёт впечатление «через одну».

## Почему Android Chrome не ломается

Chrome на Android имеет более мягкую autoplay-политику для аудио:
- Если Media Session активна и пользователь ранее взаимодействовал, Chrome разрешает `play()` на новых элементах
- Safari на iOS строго привязывает разрешение к конкретному `HTMLMediaElement`, который получил user gesture
- Это задокументировано WebKit: *«each media element must be triggered individually by the user»*

---

## Решение

Не заменять `HTMLAudioElement` при переходе. Вместо этого — переиспользовать тот же элемент, меняя ему `src`.

### Что именно изменить

1. **`prepareNextAudio`** — не нужно создавать `new Audio()`. Вместо этого можно:
   - Только предзагружать URL через `fetch()` с `Range: bytes=0-` (чтобы прогреть HTTP-кеш и TCP-соединение)
   - Или использовать `<link rel="preload" as="fetch">` для предзагрузки

2. **`startQueuedEpisode`** — убрать ветку `switchAudio(preparedAudio)`. Всегда использовать путь `primeAudioSource(audio, ...)` на существующем элементе.

3. **`switchAudio`** — можно удалить полностью или оставить только для катастрофического recovery.

### Альтернативный вариант (менее инвазивный)

Если хочется сохранить предзагрузку:
- `prepareNextAudio` готовит только данные (URL, позицию), но не создаёт `Audio` элемент
- При переходе вычисляется `src` из подготовленных данных и назначается существующему `audio` элементу
- Благодаря HTTP-кешу `load()` будет быстрым — данные уже загружены

### Что НЕ нужно делать

- Добавлять retry для `NotAllowedError` — это не поможет, Safari не изменит решение без нового user gesture
- Пытаться «перенести» user gesture между элементами — это невозможно по спецификации
- Добавлять `click()` или синтетические события — Safari их не считает user gesture

## О проблеме Android Chrome (locked screen)

Это **другой механизм** с тем же симптомом. При заблокированном экране Chrome может:
- Замедлить сетевые запросы (Doze mode)
- Задержать `canplay`/`loadedmetadata` события
- Ограничить CPU для декодирования

Код уже содержит recovery для этого (`recoverAutoPlay`, `armStartTimeout`). Исправление iOS-проблемы (убрать `switchAudio`) не должно ухудшить Android-ситуацию, потому что на Android `switchAudio` мог работать, но не был необходим.

3. **Полное решение** — переработать `prepareNextAudio` на предзагрузку данных без создания `Audio` элемента

### Раунд 2: Оценка архитектуры с new Audio() (костыль или нет?)

**Пользователь:**
> Как считаешь, предыдущая проблема закрыта корректно? Мне вот эта какая-то реализация с каким-то дополнительным аудио, кажется каким то костылем, или я ничего не понимаю?

**Ответ ассистента:**
> Ты абсолютно прав, и твоя интуиция здесь точная. Давай разберу по пунктам.
> 
> ## Это действительно костыль
> 
> **Исходная проблема** была: при заблокированном экране на Android Chrome иногда не стартует следующая глава из-за задержки сетевого запроса. Это реальная проблема — Chrome в Doze mode тормозит сеть.
> 
> **Решение, которое выбрали** — создавать заранее `new Audio()`, загружать в него следующую главу, а при переходе подменять весь элемент через `switchAudio`. Идея — раз данные уже загружены, переход будет мгновенным.
> 
> **Почему это костыль:**
> 
> 1. **Решает симптом, а не причину.** Проблема — задержка загрузки данных. А решение — дублирование аудио-элемента. Это как чинить протекающую трубу, подставляя второе ведро.
> 2. **Создаёт новую, более серьёзную проблему.** iOS Safari полностью ломается, потому что новый элемент не имеет user gesture. То есть починили Android (частично), сломали iOS (полностью).
> 3. **Переусложняет и без того сложный код.** Посмотри на [`use-playback-audio.ts`](file:///Users/cross/Desktop/VirtualBuddyShared/mpod/frontend/src/lib/use-playback-audio.ts) — 1591 строка с десятками ref-ов, generation counters, cleanup callbacks. Добавление `preparedRef`, `switchAudio`, `ownerGeneration`, `revision` делает этот код ещё сложнее для отладки. Предыдущие агенты не смогли разобраться — это прямое следствие сложности.
> 4. **Дублирует то, что браузер делает сам.** HTTP-кеш уже существует. Если сделать `fetch()` следующего аудиофайла заранее — данные попадут в кеш, и последующий `audio.src = url; audio.load()` подхватит их без сетевого запроса. Не нужен второй `Audio` элемент.
> 
> ## Что было бы правильным решением
> 
> Для предзагрузки данных следующей главы достаточно:

> ```ts

> 
> ### План исправления
> 1. **Убрать `switchAudio` и создание нового `Audio` элемента** — при переходе всегда переиспользовать тот же элемент, меняя ему `src` через существующий `primeAudioSource`.
> 2. **Заменить предзагрузку** — вместо `new Audio()` прогревать HTTP-кеш через `fetch(nextUrl, { headers: { Range: 'bytes=0-65535' } })`. Когда тот же URL назначается существующему элементу, данные берутся из кеша без задержки.
> 3. **Сохранить recovery-механизмы** для Android (таймауты, перезагрузка источника, Media Session) — они не связаны с подменой элемента.
> 
> Это решает обе проблемы: iOS получает рабочие переходы (тот же элемент сохраняет user gesture), Android сохраняет быстрые переходы (данные предзагружены в HTTP-кеш).

> *Оценка:* Идеально. Это каноничный и единственный надежно работающий паттерн для iOS Safari. Apple очень жестко привязывает User Activation (жест пользователя) к конкретному DOM-узлу. > *Важные технические детали для проверки:*  
> - *Поддержка Range на бэкенде (Go):* Убедитесь, что ваш Go-сервер корректно обрабатывает Range-запросы и отвечает статусом 206 Partial Content. Если бэкенд отдаст 200 OK и весь файл целиком, предзагрузка съест много трафика. Стандартный `http.ServeFile` в Go умеет это делать "из коробки", но если у вас кастомная отдача потока — проверьте этот момент.  
> - *Заголовки кеширования:* Чтобы браузер действительно взял данные из кеша при присвоении src, бэкенд должен отдавать правильные заголовки (например, `Cache-Control: public, max-age=...` или `ETag`). Иначе браузер может решить сделать новый запрос, проигнорировав то, что скачал fetch.  
> - *Авторизация:* Так как в требованиях указана session-based auth, не забудьте добавить в fetch нужные параметры, чтобы запрос не отвалился с 401/403:
> ```js
> fetch(nextUrl, { 
>     headers: { Range: 'bytes=0-65535' },
>     credentials: 'include' // Обязательно, если куки нужны для доступа к аудио
> });
> ```
>
