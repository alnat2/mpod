# Исследование: Скрытые Audio-пробы для выпусков без длительности

## 1. Происхождение `duration = null`

В `server/internal/podcasts/service.go`:
- Функция `parseDuration(item *gofeed.Item)` извлекает длительность только из тега `<itunes:duration>`.
- Если автор подкаста не заполнил этот тег, если он пуст, повреждён или фид использует нестандартный формат, `parseDuration` возвращает `nil`.
- В SQLite в таблице `episodes` поле `duration` сохраняется как `NULL`.
- В API `/api/podcasts/:id/episodes` и `/api/playlist` такие выпуски приходят клиенту со значением `duration: null`.
- При скачивании выпуска в `server/internal/downloads/service.go` файл сохраняется на диск, но `duration` в базе данных **не обновляется**, хотя файл уже доступен локально.
- Для аудиокниг (`server/internal/audiobooks`) проблема отсутствует, так как сканер директорий изначально использует TagLib (`ReadAudioDuration`) и сохраняет точные секунды в SQLite при первом сканировании.

## 2. Анализ поведения `useAudioMetadataDurations`

Хук `frontend/src/screens/use-audio-metadata-durations.ts` работает следующим образом:
1. Выбирает все элементы списка с `!isPositiveDuration(episode.duration) && !durationsByKey[key]`.
2. На **каждый** найденный выпуск без ограничения параллелизма создаёт отдельный объект `new Audio()`.
3. Выставляет `audio.preload = "metadata"` и `audio.src = /api/episodes/:id/audio`.
4. Браузер инициирует HTTP Range-запросы к серверу для чтения заголовков (ID3-тегов, moov-атома MP4/M4A).

### Замеры для очередей разного размера

| Размер очереди с `duration=null` | Количество создаваемых `new Audio()` | Количество HTTP Range-запросов | Сетевые соединения (HTTP/1.1) | Нагрузка и риски |
|---|---|---|---|---|
| **1 выпуск** | 1 | 1–2 (0–32 КБ) | 1 соединение | Минимальная, задержка незаметна (~50–150 мс). |
| **10 выпусков** | 10 | 10–20 (~300–800 КБ) | Упирается в лимит браузера (6 коннектов на домен) | Запросы встают в очередь (head-of-line blocking). Создаётся 10 декодеров в памяти вкладки. |
| **30 выпусков** | 30 | 30–60 (~1–3 МБ) | Жесткий contention пула соединений | Блокирует другие API-запросы (включая синхронизацию воспроизведения). Если выпуски удалённые — бэкенд одновременно открывает до 30 upstream-соединений к серверам подкастов (часто через SOCKS5-прокси), что может приводить к сетевым таймаутам. |

## 3. Оценка вариантов сохранения duration на Backend

### Вариант А: Сохранение при скачивании (`downloads.Service`) — **РЕКОМЕНДУЕТСЯ**
* **Механизм:** После завершения загрузки файла в `downloads.Service.Download()` вызывается TagLib (`ReadAudioDuration(filePath)`), и выполняется `UPDATE episodes SET duration = ? WHERE id = ?`.
* **Стоимость:** Практически 0 (локальное чтение метаданных готового файла занимает < 1 мс).
* **Эффект:** Все скачанные выпуски навсегда получают точный `duration` в БД и отдаются во фронтенд без необходимости каких-либо `new Audio()` проб.

### Вариант Б: Определение при RSS-импорте (`podcasts.Service`) — **НЕ РЕКОМЕНДУЕТСЯ**
* **Механизм:** При обновлении фида слать HTTP Range-запросы к аудио-URL каждого нового выпуска.
* **Минусы:** В фиде может быть 100–300 выпусков. Импорт станет крайне медленным (десятки секунд или минуты), вызовет подозрения на спам/DDoS со стороны серверов подкастов.

### Вариант В: Ленивое кэширование при стриминге (`episodes_handler.go`)
* **Механизм:** При отдаче стрима удалённого аудио определять длительность из заголовков ответа или первых байт.
* **Минусы:** Сложная логика перехвата Range-стрима в HTTP handler.

### Вариант Г: Ограничение параллелизма на Frontend (Concurrency Limit) — **РЕКОМЕНДУЕТСЯ**
* **Механизм:** В `useAudioMetadataDurations` вместо создания 30 параллельных `new Audio()` сделать очередь с лимитом (не более 1–2 одновременных проб), запрашивая длительность последовательно.

## 4. Рекомендуемая декомпозиция задач

1. **Backend (приоритет 1):**
   * Вынести `ReadAudioDuration` из пакета `audiobooks` в общий пакет `media` (или переиспользовать).
   * В `downloads.Service` после успешного сохранения файла вызывать чтение длительности и сохранять `duration` в таблицу `episodes`.
   * Добавить юнит-тест в `downloads`.

2. **Frontend (приоритет 2):**
   * В `useAudioMetadataDurations` добавить очередь с лимитом одновременных `Audio` (concurrency = 1..2), чтобы не блокировать сетевой пул браузера при открытии больших очередей.
