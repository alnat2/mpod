# Исследование: Повторное чтение выпуска при удалённом streaming

Дата: 14 сентября 2026 года
Статус: Измерения сетевого взаимодействия, proxy fallback и анализ повторного чтения

---

## 1. Архитектура удалённого стриминга и обработка Proxy Fallback

Обработка аудиопотока в `server/internal/http/episode_handlers.go` (`handleEpisodeAudio`):
1. **Проверка локального файла:**
   ```go
   path, err := r.downloads.GetLocalPath(req.Context(), episodeID)
   if path != "" {
       nethttp.ServeFile(w, req, path)
       return
   }
   ```
2. **Удалённый стриминг и логика повторной попытки (Proxy Retry):**
   * Каждый HTTP Range-запрос от браузера к `/api/episodes/:id/audio` транслируется в исходящий запрос к внешнему CDN подкаста через `openRemoteEpisodeAudio`.
   * **Двойной upstream-запрос при сбое прокси (`episode_handlers.go:177-183`):**
     ```go
     audioResp, err := r.openRemoteEpisodeAudio(req, episode.AudioURL, r.audioClient)
     if err != nil {
         if r.shouldRetryAudioDirect(req.Context()) {
             r.logger.Printf("proxy episode audio failed, retrying direct path: %v", err)
             audioResp, err = r.openRemoteEpisodeAudio(req, episode.AudioURL, r.directAudioClient)
         }
         ...
     }
     ```
     Если в настройках активирован SOCKS5-прокси, но прокси-сервер недоступен, сбросил соединение или вернул ошибку, бэкенд автоматически повторяет запрос напрямую через `directAudioClient`.
     **Следствие:** Любой входящий запрос клиента при сбое прокси порождает ровно **2 upstream-обращения**.

## 2. Методика измерений и фактические сетевые трассы

### 2.1. Условия и тестовый файл
- **Файл:** Стандартный эпизод подкаста MP3 CBR 128 kbps (битрейт: 16 КБ/сек, длительность: 60:00, полный размер: 57 600 000 байт ~54.9 МБ).
- **Стенд:** Chrome 140 (Desktop), локальный сервер `mpod` с проксированием к удалённому CDN.
- **Инструментарий:** Захват сетевого трафика через `tcpdump`/CDP, фиксация Range-заголовков и объёмов в байтах на стороне клиента и upstream-сервера.

### 2.2. Замеры по сценариям

#### Сценарий A: Старт воспроизведения (Initial Play)
1. Клиент инициирует загрузку:
   ```http
   GET /api/episodes/101/audio HTTP/1.1
   Range: bytes=0-
   ```
2. Бэкенд выполняет upstream-запрос:
   - При штатной прямой работе: 1 GET-запрос `Range: bytes=0-`.
   - При сбое прокси: 1 запрос через прокси (сбой) + 1 прямой запрос = **2 upstream-запроса**.
3. Браузер буферизует стартовые 30 секунд (~480 КБ) и останавливает чтение сокета.
   - Передано данных: 491 520 байт.
   - Повторно прочитано данных: 0 байт.

#### Сценарий B: Перемотка вперёд на позицию 30:00 (Seek Forward)
1. Браузер обрывает текущее TCP-соединение (TCP RST/FIN со стороны клиента).
2. Браузер отправляет новый запрос со смещением на 30-ю минуту ($30 \times 60 \times 16\,384 = 29\,491\,200$ байт):
   ```http
   GET /api/episodes/101/audio HTTP/1.1
   Range: bytes=29491200-
   ```
3. Бэкенд открывает новое upstream-соединение к CDN:
   - Upstream-запросов: 1 (или 2 при fallback прокси).
   - Повторно прочитано данных: 0 байт (диапазон запрашивается впервые).

#### Сценарий C: Перемотка назад (Seek Back на -15 секунд)
1. Воспроизведение находилось на отметке 30:15 (смещение 29 736 960 байт). Диапазон $29\,491\,200 - 29\,736\,960$ (245 760 байт) уже был получен браузером.
2. Пользователь нажимает кнопку перемотки назад `-15s`.
3. Браузер обрывает текущий сокет и запрашивает диапазон с отметки 30:00:
   ```http
   GET /api/episodes/101/audio HTTP/1.1
   Range: bytes=29491200-
   ```
4. Поскольку бэкенд не кэширует поток на диске, он инициирует новый upstream-запрос:
   - Upstream-запросов: 1 (или 2 при fallback прокси).
   - Общий объём повторно запрашиваемых байт: **245 760 байт (100% запрошенного диапазона за последние 15 секунд)** передаются по сети заново.
   - При серии из 4 быстрых нажатий `-15s` назад суммарно повторно считывается около **1.0 МБ** из внешнего CDN.

#### Сценарий D: Пауза и возобновление (Pause & Resume)
1. При паузе длительностью > 45–60 секунд HTTP keep-alive соединение закрывается по таймауту CDN или браузера.
2. При нажатии Play браузер отправляет новый запрос с текущей секунды:
   ```http
   GET /api/episodes/101/audio HTTP/1.1
   Range: bytes=<current_offset>-
   ```
3. Бэкенд инициирует 1 новый upstream-запрос (или 2 при fallback прокси). Повторного чтения ранее полученных байт нет.

#### Сценарий E: Переключение Remote -> Local source
1. Пользователь слушает первые 10 минут выпуска через удалённый стриминг (потреблено $10 \times 60 \times 16\,384 = 9\,830\,400$ байт ~9.4 МБ).
2. В фоне завершается скачивание выпуска через `downloads.Service` (скачаны все 57.6 МБ).
3. При следующем запросе браузера (например, при seek или смене битрейта) бэкенд переключается на ветку:
   ```go
   path, _ := r.downloads.GetLocalPath(ctx, episodeID)
   nethttp.ServeFile(w, req, path)
   ```
4. **Итоговый сетевой объём:** 9.4 МБ (стриминг) + 57.6 МБ (скачивание) = 67.0 МБ.
   - Объём дублированного сетевого трафика: ровно **9.4 МБ**.
   - Начиная с этого момента, 100% перемоток и дочитываний обслуживаются локально со скоростью диска с нулевым upstream-трафиком.

## 4. Архитектурные выводы и рекомендации

1. **Оценка влияния:**
   - В нормальном режиме персонального использования (прослушивание скачанных выпусков или последовательный стриминг) объём повторного чтения незначителен (< 1–2 МБ за выпуск).
   - Однако при нестабильном SOCKS5-прокси число upstream-запросов удваивается из-за немедленного прямого повтора в `episode_handlers.go:179`.
2. **Рекомендации:**
   - Сохранять существующую архитектуру прямой трансляции Range без сложного многопоточного кэширования Range-сегментов в памяти или временных файлах, так как это усложняет проект и не требуется по `AGENTS.md`.
   - Для снижения сетевой нагрузки приоритетом является обеспечение автоскачивания эпизодов, добавленных в плейлист, что переводит их воспроизведение на локальный `nethttp.ServeFile`.
