# Исследование: Повторное чтение выпуска при удалённом streaming

## 1. Текущая архитектура удалённого стриминга

Обработка аудиопотока в `server/internal/http/episode_handlers.go` (`handleEpisodeAudio`):
1. **Проверка локального файла:**
   ```go
   path, err := r.downloads.GetLocalPath(req.Context(), episodeID)
   if path != "" {
       nethttp.ServeFile(w, req, path)
       return
   }
   ```
2. **Удалённый стриминг (если файл не скачан):**
   * Каждый HTTP-запрос от браузера к `/api/episodes/:id/audio` транслируется в отдельный исходящий HTTP-запрос к внешнему CDN подкаста (`openRemoteEpisodeAudio`).
   * Заголовок `Range` из браузера напрямую передаётся в upstream-запрос к удалённому серверу.
   * Бэкенд считывает 512 байт для валидации типа медиа (`media.PreferredPlayableContentType`) и пересылает тело ответа клиенту.
   * Выставляется заголовок `Cache-Control: private, max-age=0`.
   * **Промежуточное дисковое или in-memory кэширование отсутствует.**

## 2. Анализ сетевого взаимодействия и повторного чтения

### 2.1. Старт воспроизведения (Initial Play)
* **Поведение браузера:**
  * Запрос 1: `Range: bytes=0-` (или без Range) для извлечения метаданных аудио (ID3 / MP4 moov atom) и заполнения стартового буфера (обычно 512 КБ – 2 МБ).
  * Если moov-атом находится в конце файла (для неоптимизированных M4A/AAC), браузер сразу инициирует Запрос 2: `Range: bytes=<total-32768>-<total>`.
* **Число upstream-запросов:** 1–2.
* **Объём данных:** 500 КБ – 3 МБ (только метаданные и стартовый буфер).
* **Повторное чтение:** 0 байт.

### 2.2. Перемотка (Seek)
* **Поведение браузера:**
  * Текущее TCP-соединение немедленно прерывается клиентом (`client context cancelled`).
  * Браузер открывает новый HTTP-запрос с новым смещением: например, `Range: bytes=18874368-` (перемотка на 18-й МБ).
  * Бэкенд выполняет новый upstream GET-запрос к CDN.
* **Число upstream-запросов:** 1 запрос на каждый seek.
* **Повторное чтение при перемотке назад (Seek Back, напр. -15s / -30s):**
  * Браузер запрашивает байтовый диапазон, который он уже получал ранее.
  * Поскольку бэкенд не сохраняет стрим, этот диапазон **читается из upstream повторно на 100%**.
  * При 5 перемотках назад по 30 сек (~500 КБ каждый) объём повторно прочитанных данных из upstream составляет ~2.5 МБ.

### 2.3. Пауза и возобновление (Resume)
* **Короткая пауза (< 30–60 с):**
  * Соединение сохраняется в keep-alive, дочитывание продолжается в рамках существующего соединения. Upstream-запросов: 0.
* **Длительная пауза / блокировка экрана / сброс вкладки мобильным браузером:**
  * Соединение закрывается.
  * При нажатии Play браузер отправляет новый `Range: bytes=<position>-`.
  * Бэкенд выполняет 1 новый upstream-запрос.

### 2.4. Переключение Remote -> Local source
* **Сценарий:** Пользователь слушает удалённый эпизод, и в этот момент фоновый процесс скачивает выпуск на диск (`downloads.Service`).
* **Поведение:**
  * Фоновый загрузчик скачивает файл целиком: `N` МБ (100% файла).
  * До момента окончания загрузки пользователь через стриминг потребил, например, `M` МБ (допустим, 15 МБ из 60 МБ).
  * **Объём дублированного сетевого трафика:** ровно `M` МБ (первые 15 МБ были скачаны дважды: один раз через стриминговый прокси, второй раз фоновым скачиванием).
  * После завершения скачивания следующий запрос браузера (например, при следующем seek) мгновенно подхватывается веткой `ServeFile` без сетевых обращений к upstream.

## 3. Сводная таблица измерений

| Сценарий | Upstream-запросы | Трафик upstream | Объём повторно прочитанных данных |
|---|---|---|---|
| **Обычный старт и непрерывное слушание** | 1 (длинный стрим) | Равен размеру прослушанного аудио | 0 байт |
| **Seek вперёд (+30s / +1m)** | +1 на каждый seek | Только новый диапазон | 0 байт |
| **Seek назад (-15s / -30s)** | +1 на каждый seek | ~250–500 КБ за каждый шаг | 100% запрошенного диапазона (~250–500 КБ) |
| **Возобновление после закрытия соединения** | 1 | С текущей секунды до конца | 0 байт |
| **Слушание 20% выпуска + фоновое скачивание** | 1 стрим + 1 фоновый download | 120% от размера файла | 20% размера файла дублируется |

## 4. Рекомендации по оптимизации

В соответствии с правилами проекта: *«Не внедрять кэширование или новую transport-архитектуру без подтверждённой стоимости и отдельного решения Team Lead»*.

1. **Текущее поведение приемлемо для MVP:**
   * В персональном однопользовательском приложении пользователь редко делает десятки прыжков назад по одному и тому же треку.
   * Основной сценарий воспроизведения — либо последовательное прослушивание, либо воспроизведение предварительно скачанных выпусков из плейлиста.
2. **Будущая оптимизация (если потребуется):**
   * Если выпуск находится в плейлисте, инициировать его фоновую загрузку в `downloads`, чтобы после скачивания он сразу отдавался локально.
   * Не реализовывать сложный HTTP range proxy cache на Go без острой необходимости, так как поддержка частичных диапазонов, сброса по LRU и инвалидации создаёт высокую архитектурную сложность при скромном реальном выигрыше в однопользовательской системе.
