# Тестирование на эмуляторах и симуляторах

Обязательный документ перед любым прогоном тестов на эмуляторах/симуляторах и перед задачами
вида «проверь в браузере/на устройстве». Содержит правила запуска и дисциплину работы,
а в конце — актуальный тест-план PWA mpod.

---

## 1. Разрешение на запуск

- Тестирование начинается только по явной команде: «запускай», «поехали», «проведи тест».
- Вопросы вида «можешь запустить?», «получится?», «сколько займёт?» — это запрос информации,
  а не разрешение. На них отвечаем описанием плана и ждём команды.
- Разрешение одноразовое: покрывает один прогон. После паузы, остановки или завершения
  следующий запуск требует новой команды.
- Остановка («стоп», «пауза», «подожди») выполняется немедленно и не возобновляется
  без отдельной команды «продолжай».
- Подготовка окружения (поднять эмулятор, сервер, поставить драйвер) — тоже часть запуска.
  До команды стенд не поднимается, кроме случая, когда пользователь прямо просит его поднять.
- Запуск в отдельном чате/потоке — такое же действие, как запуск на месте: только по команде.

## 2. Готовность окружения

Проверить и записать в отчёт до первого кейса:

| Проверка | Как | Ожидание |
|---|---|---|
| Стенд отвечает | `curl -s -o /dev/null -w "%{http_code}" <URL>/api/auth/session` | 200 |
| Сессия/логин | открыть приложение на устройстве | вход выполнен или известны рабочие креды |
| PWA установлена | иконка на домашнем экране | присутствует |
| Эмулятор запущен | список устройств | нужный девайс в статусе booted |
| Инструментарий | CDP / agent-device / adb отвечают | все команды выполняются успешно |
| Скрипты готовы | файлы на месте, синтаксис проверен | запуск без доработок «по ходу» |

Не хватает чего-то — стоп и сообщение пользователю. Никаких установок и импровизаций посреди прогона.

## 3. Дисциплина команд

- Каждая команда к устройству/эмулятору — под `timeout 90`. Зависшая команда — не «ещё немного
  подождать», а прерывание и запись в п. 7.
- Запрещены `Page.reload` и любые блокирующие навигации в состоянии offline/Doze: только новые
  табы или перехват запросов.
- Один скрипт на кейс вместо 4–5 round-trip'ов (тап → settle → снапшот → скриншот → чтение).
- Состояние (логин, кеши, сеть, флаги) меняется через CDP, а не тапами. Тапаем только то,
  что само является предметом проверки.
- UI-действия — только через `agent-device` (`device_open` → путь из ответа). Тапы по координатам —
  крайний случай, после `snapshot -i`.
- Через `adb` разрешено только то, чего `agent-device` не умеет: `forward`, `dumpsys deviceidle`,
  `input keyevent` для power, чтение логов, `emu kill`.

## 4. Регресс ≠ диагностика бага

**Регресс-прогон** (проверяем, что фичи живы): фиксированная матрица кейсов, прогон от начала
до конца, таблица Pass/Fail.

**Диагностика бага** (надо понять причину и починить): матрицу кейсов не пишем. Порядок:

1. Воспроизвести баг по-человечески и зафиксировать эталон.
2. Инструментировать и найти точку обрыва — один-два прогона, только нужные измерения.
3. Минимальный фикс.
4. Проверить фикс тем же человеческим сценарием плюс контроль «раньше работало».

Исследования «а как на 60 секундах, а на 300» — вне задачи, если пользователь не просил
описать поведение системы.

## 5. Фиксация результатов и пауза

- После каждого кейса — строка в таблицу результатов: платформа, PASS / FAIL / не проверено, артефакт.
- Таблица пишется сразу, а не в конце: пауза должна оставлять пригодный отчёт.
- Артефакты — в одном каталоге, имена `<платформа>-<кейс>-<шаг>.png`.
- При остановке — короткая сводка: что успели, что нет, что осталось запущенным.

## 6. Стенд и границы

- Тесты идут только на стенде, указанном в плане. Локальный сервер — только если он в плане
  или пользователь попросил явно.
- Для диагностики воспроизводим на том же стенде, где баг замечен.
- Всегда запрещено: deploy, SSH на внешние хосты, коммиты и push, изменения продуктового кода
  в рамках прогона (кроме шага «фикс», если задача про баг).

## 7. Известные ловушки окружения

- **Pixel_9 (API 37):** Chrome иногда рендерит чёрный экран (в том числе на `example.com`) —
  это окружение, а не приложение. Проверять на стороннем сайте прежде чем искать баг в продукте.
- **CDP на Android:** `Page.reload` в offline/Doze подвисает без ответа — не использовать.
- **iOS Simulator:** локскрин и MediaRemote ведут себя иначе, чем на реальном iPhone;
  для media session симулятор не является доказательством.
- **Локальная БД:** пользователь `admin`, пароль не хранится в репозитории — запрашивать заранее.

## 8. Формат отчёта

- Таблица кейс × платформа × результат.
- Явная колонка «чем проверено»: автотест / руками / эмулятор / реальное устройство.
- Фраза «не проверено» обязательна там, где не проверяли. Косвенное доказательство нельзя
  выдавать за прямое.

# Тест-план: отказоустойчивость PWA mpod (ветка `test`)

## Контекст задачи

В ветке `test` были реализованы исправления для устойчивости PWA при старте и выходе из фона:

- Устранён ложный экран «mpod is not reachable» при задержках мобильной сети / подключении VPN
  (300–1200 мс) за счёт ограниченных повторных попыток (bounded retry loop с экспоненциальной задержкой).
- Добавлено автоматическое восстановление при возврате сети (`online` event) без клика по «Retry».
- Реализована очистка устаревших кешей API (`api-session-cache`, `api-playback-cache`,
  `api-data-cache`) из Cache Storage на старте.
- Интегрирована отмена (`AbortController`) зависших запросов сессии при размонтировании
  и повторном запуске.

Целевой коммит с полным набором PWA-фиксов: **`c31b204`** (или актуальный `HEAD` ветки `test`:
**`c37218f`**).

## Данные для подключения

- **URL тестового стенда:**
  - **Основной тестовый стенд (NAS):** `http://192.168.0.222:5051`
  - **Локальный сервер на хост-машине (если поднят локально):**
    - iOS Simulator: `http://localhost:5050`
    - Android Emulator: `http://10.0.2.2:5050` (в Android Emulator `localhost` указывает на сам
      эмулятор, для доступа к Mac используйте `10.0.2.2`)
- **Авторизация (single-user):**
  - Логин: `admin` (или `qa`); пароль: `secret`
  - Если база чистая (`setupRequired: true`), приложение откроет `/setup` («Create your account») —
    зарегистрируйте пользователя `admin` с паролем `secret`.

## Подготовка и установка PWA

1. Откройте тестовый URL в браузере эмулятора: Android — Google Chrome, iOS — Safari.
2. Войдите под указанными креденшалами.
3. Установите PWA на рабочий стол эмулятора:
   - Android Chrome: меню (три точки) → «Add to Home screen» (или «Install app»).
   - iOS Safari: «Поделиться» → «Add to Home Screen».
4. Все дальнейшие тесты запускаются **с иконки на домашнем экране** (как отдельное PWA-приложение).

### Управление сетью в эмуляторах

- **Android Emulator:** шторка быстрых настроек — тумблер Airplane mode; окно Extended controls
  (кнопка `...`) → вкладка Cellular → Network type (`LTE`, `UMTS/3G`, `GPRS`).
- **iOS Simulator:** утилита macOS Network Link Conditioner (профили `3G`, `Very Bad Network`,
  `100% Loss`).

## Тест-кейсы

### Кейс 1: Холодный старт при задержке сети / подключении VPN

> Раньше при запуске PWA с рабочего стола интерфейс загружался из кеша за 20 мс, а пока мобильный
> модем или VPN подключались к сети (300–800 мс), первый сетевой запрос падал, и пользователю сразу
> выводилась ошибка «mpod is not reachable».

**Шаги:**

1. Закройте PWA mpod (выгрузите из списка запущенных свайпом).
2. Задайте искусственную задержку: Android — Extended controls → Cellular → `UMTS`/`GPRS`
   (или включите и выключите Airplane mode за 1 с до запуска); iOS — профиль `3G`.
3. Нажмите иконку **mpod** на домашнем экране.

**Ожидаемый результат:**

- Экран «mpod is not reachable» **не появляется**.
- Виден спиннер загрузки, приложение делает до 3 попыток с задержками 400 и 800 мс.
- Через 1–2 секунды после стабилизации связи открывается домашний экран.

### Кейс 2: Старт полностью офлайн и автовосстановление

**Шаги:**

1. Выгрузите PWA из памяти.
2. Включите Airplane mode.
3. Запустите PWA с домашнего экрана.
4. Подождите ~2 секунды (3 попытки исчерпаны).
5. Появился экран «mpod is not reachable» с кнопкой «Retry».
6. **Не нажимая** «Retry», выключите Airplane mode.
7. Вернитесь в окно PWA.

**Ожидаемый результат:**

- Приложение перехватывает событие `online`.
- Экран ошибки сам сменяется индикатором загрузки, домашний экран открывается без клика.

### Кейс 3: Восстановление по кнопке «Retry»

**Шаги:**

1. В офлайне запустите PWA и дождитесь экрана «mpod is not reachable».
2. Включите сеть.
3. Нажмите «Retry».

**Ожидаемый результат:** экран ошибки сменяется индикатором загрузки, приложение открывает
домашний экран без зависаний и мерцаний.

### Кейс 4: Возобновление из фона (Passive Refresh)

**Шаги:**

1. Откройте PWA, убедитесь, что на домашнем экране (или играет аудио).
2. Сверните приложение.
3. Подождите 15–20 секунд.
4. Вернитесь в PWA.

**Ожидаемый результат:** мгновенное восстановление без белого экрана и без сброса в глобальный
спиннер; фоновое обновление сессии не прерывает плеер.

### Кейс 5: Истечение сессии (401)

**Шаги:**

1. Откройте PWA (пользователь залогинен).
2. Через DevTools или CDP удалите session-cookie (logout через UI даёт другой сценарий).
3. В PWA перейдите на другую страницу или сверните/разверните приложение.

**Ожидаемый результат:** 401 распознаётся как отказ авторизации, а не сетевая ошибка; приложение
**не делает** 3 попытки и **не показывает** «mpod is not reachable», а сразу уводит на `/login`.

### Кейс 6: Очистка устаревших кешей

**Шаги:**

1. Подключите инспектор: Android — `chrome://inspect/#devices` → Inspect; iOS — Safari → Develop.
2. Application (в Safari — Storage) → Cache Storage.
3. В Console: `await caches.keys()`.

**Ожидаемый результат:**

- Отсутствуют `api-session-cache`, `api-playback-cache`, `api-data-cache`.
- Присутствуют только `workbox-precache-...`.
- Запросы `/api/auth/session` идут напрямую в сеть (Status 200, size в байтах, а не `(ServiceWorker)`).
