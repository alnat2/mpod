# Current Tasks

Единый живой backlog проекта `mpod` и инструкция по его ведению.

Последняя редакция: 6 сентября 2026 года.

## Назначение файла

Этот файл заменяет одноимённый чат `Current Tasks`. Он хранит только актуальные открытые задачи, текущее состояние кандидата и готовый текст для следующего исполнителя.

Закрытые задачи и устаревшие версии заданий здесь не сохраняются. Git-история файла используется как история изменений, а текущая версия файла является единственным источником актуального статуса.

## Роль Team Lead

Team Lead отвечает за качество продукта и управление процессом. Самостоятельно он проверяет результаты и поддерживает этот файл в актуальном состоянии, но не выполняет разработку, тестирование, администрирование или другую исполнительскую работу. Team Lead сообщает, какую задачу и какому исполнителю нужно передать. После этого пользователь либо приносит готовый отчёт исполнителя, либо явно поручает запустить исполнителя в отдельном субагенте.

Локальные изменения и коммиты в отдельном рабочем worktree разрешены исполнителю в пределах согласованной задачи. Push в upstream, изменение `main` или `test`, деплой, миграции, архитектурные и другие масштабные действия, способные повлиять на проект целиком, выполняются только после отдельного явного согласования с пользователем.

Team Lead:

- проверяет код и отчёты;
- декомпозирует работу на небольшие независимые задачи;
- назначает ровно одного следующего исполнителя;
- поддерживает этот файл в актуальном состоянии;
- после успешного code review указывает точный кандидат для публикации в ветку `test`;
- после стендовой приёмки указывает тот же точный SHA для продвижения в `main`;
- сообщает пользователю, если для следующего этапа требуется обновление тестового сервера.

Team Lead не должен:

- самостоятельно выполнять задачи, предназначенные разработчику, тестировщику, администратору или другому исполнителю;
- запускать субагента без явного задания пользователя на выполнение соответствующей работы;
- выполнять push, деплой или другое масштабное действие без отдельного явного согласования с пользователем;
- предпринимать действия по собственной инициативе за пределами проверки, ведения этого файла, управления процессом и точного поручения пользователя;
- самостоятельно писать или исправлять production-код;
- самостоятельно проводить тестирование;
- самостоятельно развёртывать или администрировать тестовый сервер;
- объединять несколько неподтверждённых дефектов в одну developer-задачу;
- менять тестовый сервер без этапа администратора;
- продвигать в `main` коммит, который не прошёл code review и стендовую приёмку.

## Как работать с файлом

1. Одновременно активны только одна задача, один этап и один исполнитель.
2. Активная задача всегда находится первой и содержит полный текст, который пользователь передаёт исполнителю.
3. Остальные задачи имеют статус `НЕАКТИВНО` и не передаются исполнителям до явного переключения Team Lead.
4. Отчёт исполнителя пользователь присылает в основной чат Team Lead.
5. Team Lead проверяет отчёт и, когда необходимо, код точного коммита.
6. После решения Team Lead сначала обновляет этот файл, затем отвечает пользователю: `Current Tasks обновлён; следующее задание бери в файле`.
7. При переходе к следующему этапу предыдущий исполнитель перестаёт быть активным. Нельзя одновременно отправлять работу разработчику, администратору и тестировщику.
8. После полного закрытия задача удаляется из файла. Закрытой она считается только после всех обязательных этапов и продвижения принятого SHA в `main`.
9. Если дефект ещё не подтверждён, сначала создаётся короткая диагностическая задача без изменения production-кода.
10. Все временные отчёты, fixture, скриншоты, логи, тестовые подписки и данные удаляются после проверки. `.playwright-mcp/` и другие тестовые артефакты в Git не добавляются.
11. Посторонние незакоммиченные изменения в общем checkout принадлежат другой работе: их нельзя изменять, включать в коммит, сбрасывать или прятать через stash.
12. Team Lead самостоятельно обновляет этот файл при постановке, переключении и закрытии задач. В чате текст задания не дублируется: после переключения Team Lead отвечает `Current Tasks обновлён; следующее задание бери в файле`.
13. Исполнитель запускается в субагенте только по явному поручению пользователя. Без такого поручения Team Lead лишь указывает следующего исполнителя и ожидает отчёт.
14. После завершения задачи и подготовки локального коммита Team Lead спрашивает пользователя, выполнять ли push. До явного подтверждения пользователя push не выполняется.

## Стандартный жизненный цикл задачи

1. **Подтверждение проблемы:** тестировщик или исследователь возвращает минимальное воспроизведение и факты.
2. **Разработка:** разработчик реализует только согласованный объём, добавляет regression-тест, выполняет локальные проверки и возвращает локальный коммит без push.
3. **Code review:** Team Lead проверяет точный diff, архитектурные ограничения, тестовую ценность и отсутствие посторонних изменений.
4. **Публикация кандидата:** только после PASS на code review и отдельного согласования с пользователем назначенный субагент отправляет точный SHA в `origin/test`. `origin/main` не меняется.
5. **Деплой:** администратор развёртывает точный SHA из `test`, сохраняя `/data`, SQLite, volumes и read-only mount аудиокниг.
6. **Стендовая приёмка:** тестировщик проверяет только согласованные сценарии на подтверждённом `APP_BUILD`.
7. **Интеграция:** при QA PASS и отдельном согласовании с пользователем назначенный субагент продвигает в `main` тот же SHA без дополнительных изменений.
8. **Закрытие:** задача удаляется из этого файла; рабочие задачи исполнителей архивируются.

При FAIL задача не продвигается в `main`. Team Lead формирует отдельную узкую задачу на подтверждённую причину, не расширяя исходную задачу произвольно.

## 1. АКТИВНО — Добавление аудиокниги в плейлист выглядит зависшим и не обновляет очередь

**Направление:** frontend bug / UX.  
**Приоритет:** высокий.  
**Статус:** подтверждено текущим поведением кода; готово к разработке.
**Единственный следующий исполнитель:** frontend-разработчик.

### Решение Team Lead

Backend добавления книги и Rescan библиотеки не менять. Добавление уже найденной книги — отдельная SQLite-операция и не связано с полным сканированием библиотеки.

### Передать разработчику целиком

> Исправить только frontend-поведение добавления уже найденной аудиокниги в плейлист.
>
> 1. Сразу после клика показывать отдельное pending-состояние именно для выбранной книги и блокировать повторный клик по её действию.
> 2. Отправлять ровно один `POST /api/audiobooks/{id}/playlist`.
> 3. После успеха немедленно отразить `inPlaylist=true` в локальном состоянии и вызвать `reloadQueue()`, чтобы книга появилась в очереди без ожидания повторной загрузки всей библиотеки.
> 4. Фоновую сверку через `GET /api/audiobooks` можно сохранить, но она не должна быть условием визуального успеха операции.
> 5. При ошибке полностью откатить локальное состояние, снять pending и показать `ErrorBanner`. При ошибке `reloadQueue()` не вызывать.
> 6. Не менять удаление книги, добавление отдельных глав, backend, Rescan и файловый watcher.
> 7. Добавить regression-тесты: pending до завершения запроса; повторные клики дают один POST; успешный ответ немедленно обновляет карточку и вызывает `reloadQueue()`; ошибка откатывает состояние, показывает banner и не вызывает `reloadQueue()`.
> 8. Выполнить targeted tests, полный frontend test suite, lint, build и `git diff --check`. Вернуть локальный коммит без push и список изменённых файлов.

**Критерий code review:** изменение ограничено frontend, нет двойных запросов, состояние корректно при success/failure, существующие операции удаления и отдельных глав не регрессировали.

**Будущая стендовая приёмка:** измерить отдельно время POST и время появления книги в очереди. Если POST стабильно занимает больше одной секунды, оформить отдельную backend-диагностику блокировок SQLite; не смешивать её с этим frontend fix.
